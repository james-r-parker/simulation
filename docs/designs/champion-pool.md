# Champion pool

**Status:** Proposed - a per-season pool of trained champions in D1 seeds new worlds, and browsers capture, test and submit the lineages worth keeping; Phase 1 (pool export, PR, release seed) first, after [training.md](training.md) T16.
**Validated:** 26ae0c51 (2026-11-18)
**Scheduled by:** [training-loop.md](training-loop.md) step 5 - the closed loop from trained champions to a seeded pool and back; it builds on the trainer and the exam
**Depends on:** [training.md](training.md), [training-stages.md](training-stages.md), [deployment-and-community.md](deployment-and-community.md), [worker-and-renderer.md](worker-and-renderer.md), [brain-reflex-tests.md](brain-reflex-tests.md)

> Companion to [deployment-and-community.md](deployment-and-community.md): that doc owns the gene library, sign-in, the upload endpoint and the nightly league verification. This doc owns what feeds them and what they feed.

A closed loop. Trained champions become a per-season pool in D1. A new world draws its founders from the pool. A browser notices a lineage worth keeping and tests it. The player may submit it. A nightly runner re-verifies it with the repo's own code. A verified champion joins the pool.

```
trainer -> exam + league -> library/champions/<season>/ (PR) -> release deploy -> D1 pool
   ^                                                                                  |
   |                                                                                  v
verified row joins the pool  <-  nightly re-verification  <-  submit  <-  local test  <-  new world: founders from the pool
```

## Scope

The scenes it serves ([principles.md](../principles.md)): **Same spec, different custom** (a pool spread over style bands and cells seeds more than one predator line), **A real chase** and **Leave a dying patch** (founders that already hold the skill start the world with the scene on screen). Selection rules it enforces: rule 2 (a champion is ranked by exam result and league Elo, never by training fitness), rule 4 and rule 9 (a browser keeps a lineage that survived a hard stretch and whose grandchildren repeat the skill), rule 1 (whether floor refills draw champions is measured both ways, Phase 2).

Out of scope: any fitness term, any sim rule, any change to `worldHash` of a world that has no pool, the sign-in and moderation of [deployment-and-community.md](deployment-and-community.md) Phase 3.

## Pool

A pool is the champions one season holds for seeding.

- **Size.** At most `POOL_PER_SPEC` (10) champions per specialisation per season.
- **Rank.** `poolRank(row)` orders by the number of drills whose `edgeLow` is above 0 (exam row 3, [training-stages.md](training-stages.md), The exam), then by league Elo; the per-file figures are stored in the row's `exam` JSON. The exam's set-level rows (4, 8 and 9) gate `npm run pool:export` as a whole and never rank a file. A training fitness or a lower bound never enters the rank.
- **Spread.** `selectPool({ rows, bandOf })` takes rows in rank order and skips a row when its cell already holds `CELL_CAP` (2) pool rows or its style band already holds `POOL_PER_SPEC / STYLE_BANDS` (5) rows of the specialisation. `bandOf` is `styleBandOf` from [champion-export.js](../../js/evo/champion-export.js), injected so `js/library/` imports nothing outside itself.
- **Bar.** `poolBar(rows)` is, per specialisation, the lowest `exam.reflexScore` and the lowest `exam.drillEdgeLow` among its pool rows. A candidate clears the bar when it is at least both.
- **Retire.** A row displaced from the pool keeps its row and its file: `in_pool` becomes 0 and `retired_at` is stamped. Nothing is deleted. A retired file stays in git, so a replay of a world seeded from it still resolves.
- **Empty.** A season with no pool rows (a rules change opens a season before its pool exists) is not an error. Seeding falls back to random brains and logs `ChampionPoolEmpty`.

### Data

`migrations/0003_pool.sql` adds to `champions` (the table of [deployment-and-community.md](deployment-and-community.md), Phase 2, Data):

| Column       | Type                       | Holds                                                                                                                                                                                                                                        |
| ------------ | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `in_pool`    | INTEGER NOT NULL DEFAULT 0 | 1 while the row is in its season's pool                                                                                                                                                                                                      |
| `retired_at` | INTEGER null               | Unix second the row left the pool                                                                                                                                                                                                            |
| `provenance` | TEXT null                  | JSON: for a trained champion `{ kind: "trained", run, generation, sha }`; for an upload `{ kind: "found", seed, config, rulesHash, appVersion, tick, lineageDepth, genomeIds, lineageId, policy, poolIds, interventions, replayable, hint }` |
| `exam`       | TEXT null                  | JSON: `{ passed, rows, reflexScore, drillEdgeLow, league: { elo, winRate, games } }`, written by the pool export and by the verifier                                                                                                         |

Index `champions_pool` on `(season, in_pool, specialisation, elo DESC, id)`. `GET /api/champions` gains the query parameter `pool=1` (rows with `in_pool = 1` only); the app asks `/api/champions?spec=<n>&limit=10&pool=1`. A row's `provenance` and `exam` are public fields of `toPublicChampion` ([rows.js](../../js/library/rows.js)).

### Files in the repository

`library/champions/<season>/` holds one canonical champion file per pool member (`<id>.json`, `canonicalChampion` bytes from [canonical.js](../../js/library/canonical.js)) and `index.json`: `[{ id, specialisation, cell, style, elo, exam, provenance }]`. A `conventions` test (`test/library/pool-files.test.js`) fails when a file does not pass `validateChampion` ([league.js](../../js/evo/league.js)) against the season's `rulesHash` in `library/seasons.json`, when a file name is not its content id, when `index.json` disagrees with the files, or when `selectPool` over the index would not return the same set.

## Phases

### Phase 1 - Pool export and the D1 seed

**Targets:** none - infrastructure; the files, the SQL and the deploy step are pinned by tests, and no `bench.*`, `browser.*` or `eval.*` metric moves

Waits on [deployment-and-community.md](deployment-and-community.md) Phase 2 (the `champions` table, `/api/champions` and the seed script built), on [training.md](training.md) T16 showing, on 16 seeds, that `champions-v1` beats the live policy, and on [training-stages.md](training-stages.md) T22 (`npm run train:exam`).

#### Export

`npm run pool:export -- --run <dir> --season <n> [--dry-run]` (`scripts/pool-export.mjs`, with `scripts/lib/pool-files.mjs`):

1. Reads the run's `exam.json` and the champion files `train:export` wrote ([champion-export.js](../../js/evo/champion-export.js), `exportBestPerStyle`).
2. Reads each champion's Elo from `evals/league.json`; a champion not yet admitted is refused with its name (`npm run league -- <file> --admit` first).
3. Merges them with the season's existing `library/champions/<season>/index.json`, runs `selectPool`, and writes the files and the index. Files that leave the pool stay in the directory; `index.json` lists only the pool.

`--dry-run` prints the pool and the rows `selectPool` skipped, each with its reason (`cell_cap`, `band_cap`, `rank`).

#### Release seed

The release build job (no secrets) runs `node scripts/library-pool-sql.mjs`, which builds `library-pool.sql` with `buildSeedRows`, `championsSql` and `filesSql` ([seed.js](../../js/library/seed.js)) for every file in `library/champions/<season>/` (the `in_pool` and `retired_at`, `provenance` and `exam` columns included), then one `UPDATE` per season that sets `in_pool = 0` and `retired_at` on official rows (null `uploader_id`) not in the index. The statements are idempotent (`INSERT OR REPLACE` by content id). The file joins the `release` artifact of [deploy.yml](../../.github/workflows/deploy.yml). The deploy job runs `wrangler d1 execute blob-library --remote --file library-pool.sql` after `wrangler d1 migrations apply` and before the Pages deploy; it runs no repository script. A rollback to an earlier release re-runs that release's own `library-pool.sql`, so the pool rolls back with the release. Agents never write D1.

### Phase 2 - Seeding worlds from the pool

**Targets:** eval.hunter_catches_per_1k, eval.food_energy_per_1k, eval.births_per_1k, eval.predators_at_end

A world draws founders from the current season's pool. The draw is a policy option, so `rulesHash` does not change.

#### Draw

`createChampionDraw({ champions, randomShare, floor })` in `js/evo/policies/champion-draw.js` is the draw `createChampionsV1` ([training.md](training.md) T15) calls: one code path, replacing the file reading `createChampionsV1` has when T15 has landed. It plugs into `createSeeder` ([map-elites-seed.js](../../js/evo/policies/map-elites-seed.js)) as the option `champions`, beside `opponents` ([map-elites-pool.js](../../js/evo/policies/map-elites-pool.js), `createPoolDraw`):

- The seeder picks the specialisation first (`initSpec`). The draw then takes, with probability `1 - randomShare` (`randomShare` defaults to `0.25`), a pool champion of that specialisation, uniform over the pool rows, and writes its weights with the sigma of an archive-child draw (`mutateSigma`, `mutateWeights` of [mutation.js](../../js/evo/mutation.js)). Otherwise the seeder's own draw runs unchanged.
- `floor` defaults to `false` until T19: the draw acts only while `world.tick` is 0, so floor refills (`fillFloor` in [population.js](../../js/sim/population.js)) use the seeder's own draw. With `floor` `true`, floor entrants draw champions too.
- A specialisation with no pool champion falls through to the seeder's draw. An empty pool logs `ChampionPoolEmpty` once and draws nothing.
- With `randomShare` 1, with no pool, or with an empty pool, the draw consumes no random numbers, so the world and its `worldHash` equal the no-option world's.
- Founders drawn from the pool join `poolFounders`'s sibling set `championFounders` (genome ids), so the observer can tell their descendants.

#### Options and sources

| Source                                         | How the pool arrives                                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Headless (`eval`, `replay`, `screen`, `train`) | The policy option `championPool` `{ dir, randomShare, floor }` (in `--policy-options`; `replay --pool <dir> --pool-share <x> --pool-floor`); `loadPoolDir(dir, config)` in `scripts/lib/pool-load.mjs` reads `<dir>/index.json` and the files, validates each with `validateChampion` and passes them in file-id order                           |
| Browser                                        | `fetchPool({ fetch, season })` in `js/app/pool-client.js` asks `/api/champions?spec=<n>&limit=10&pool=1` for each specialisation, then each `/api/champions/:id/file` (immutable, cached by the browser), with a 3 s timeout; the files go in the `init` and `reset` message field `pool`; `?pool=off` skips the fetch and seeds random founders |

A failed or timed-out fetch falls back to the files bundled at `public/champions/v1/` when that season's `rulesHash` matches, otherwise to random founders, and logs `PoolFetchFailed`. The world starts after the fetch resolves or times out; it never waits longer than the timeout.

#### Screen

`evals/screens/champion-pool.grid.json`: arms `random` (no pool), `founders` (`randomShare` 0.25, `floor` false) and `founders-floor` (`floor` true), 32 seeds, 200000 ticks, the pool of T9. Prediction first, written in the grid's header before the run: hunters start the world already closing and biting, so `eval.hunter_catches_per_1k` and `eval.predators_at_end` read higher under `founders` than `random`, and `eval.food_energy_per_1k` does not read lower; `founders-floor` reads higher on `eval.predators_at_end` and no better on the others, which selection rule 1 predicts (a refill from champions edges toward rescue). `npm run eval:compare -- <random> <founders> --keep-rule` gives the verdicts. T19 sets the default of `floor` from the result and deletes the losing path and the option when `floor` has a single winning value.

### Phase 3 - Candidate capture and the local test

**Targets:** bench.observe_ms@500, browser.frame_p95_ms, browser.draw_cpu_p95_ms

Waits on [worker-and-renderer.md](worker-and-renderer.md) Phase 5 (`archive-store.js`, IndexedDB version 2, `init.fresh`). A browser notices a lineage, not a score. Everything here is observer-side: no field in `worldHash`, no fitness term, no sim rule.

#### Worth keeping

`js/evo/scene-keeper.js` (`createKeeperScene`, `noteKeeperBirth`, `noteKeeperDeath`, `tickKeeper`, `keeperCandidates`), registered in `js/evo/detectors.js` as a detector (registries.md Phase 3) like the recruit scene ([scene-recruit.js](../../js/evo/scene-recruit.js)). A lineage nominates one genome when all hold:

1. **A hard stretch.** The lineage was alive through at least one of: a winter ([eras.js](../../js/sim/eras.js) season), a population crash (the world under 40% of its peak over `KEEPER_WINDOW_TICKS`), or a stretch of `KEEPER_HUNTED_TICKS` with a hunter within `callRadius` of one of its members.
2. **The grandchildren repeat the skill.** At least `KEEPER_GRANDCHILDREN` (4) grandchildren of the nominee, born after the stretch began, each performed the skill of the specialisation: a hunter made a deliberate kill, a forager left a depleted patch, prey escaped a chase (the counters of [observer-lineage-counters.js](../../js/evo/observer-lineage-counters.js)). Descendants of a pool founder count like any other.
3. **Alive.** The nominee is alive at the tick of capture and `interventions` (world-changing commands the page sent) is 0. `select` and `setLenses` change nothing in the world and do not count.

A scene detector that fires rarely (`eval.alarm_rate` style detectors named in [scene-scorecard.md](../scene-scorecard.md)) may nominate a genome through `noteKeeperScene`, subject to condition 3. The scene keeps preallocated typed arrays per lineage slot and a ring of `KEEPER_MAX_PENDING` (8) nominations; a tick allocates nothing. A world nominates at most one candidate per `KEEPER_COOLDOWN_TICKS`.

`buildCandidate(world, nominee, run)` in `js/evo/candidate.js` returns `{ file, provenance }`: `file` is the champion file of the nominee's specialisation, layout and weights (name `<lineage>-<tick>`), `provenance` the object of the Data table with `replayable` true only when the world began from a seed with no resumed archive (`fresh` of the `init` message, [worker-and-renderer.md](worker-and-renderer.md) Phase 5), `poolIds` the ids of the pool files the world was seeded from, and `genomeIds` the nominee's ancestry back to its founder. `hint` holds the local test result and is never read by the server.

#### Protocol

The sim worker posts `candidate { file, provenance }` (new to-main type in [protocol.js](../../js/worker/protocol.js), validated by `validateMessage`). The main thread forwards it to the candidate worker and does nothing else with it.

#### Local test

`js/evo/local-test.js` (`createLocalTest`, `stepLocalTest`, `testVerdict`): the candidate's specialisation's reflex cases (`casesFor` in [reflex-cases.js](../../js/evo/reflex-cases.js), `evalReflex` in [reflex-eval.js](../../js/evo/reflex-eval.js)) and the drills that apply (`drillSubject` in [drill.js](../../js/evo/drill.js)), each against `poolBar(rows)` of the pool the page fetched. `stepLocalTest(test, { budgetMs, now })` runs trials until `now()` passes `budgetMs` and returns, so a test is a series of slices of at most 4 ms; the result is `{ clears, reflexScore, drillEdgeLow, trials }`. The test is deterministic: the same candidate and bar give the same result.

`js/worker/candidate-worker.js` runs the test in its own worker (imports `js/evo/` only), started by `js/app/candidates-client.js` when `createIdleTracker` ([idle.js](../../js/app/idle.js)) reports idle for 30 s and `navigator.hardwareConcurrency` is at least 4, and terminated when the frame ring ([frame-stats.js](../../js/app/frame-stats.js)) reads `browser.frame_p95_ms` above 4.4 ms or the page is hidden. A terminated test restarts from the candidate's first slice. One candidate is tested at a time. The result is a hint: a candidate that fails is kept, marked `clears: false`.

#### Candidate store

`js/worker/candidate-store.js` (`openCandidateStore`, `putCandidate`, `listCandidates`, `markSubmitted`, `clearCandidates`) keeps candidates in the object store `candidates` of IndexedDB `BlobEvolutionDB`, keyed by the file's content id, over an injected `indexedDB` factory. The schema version is the one after [worker-and-renderer.md](worker-and-renderer.md) Phase 5's (2), so 3; the upgrade from 2 creates the store and touches nothing else. At most `CANDIDATE_KEEP` (20) are kept: past that the oldest unsubmitted is dropped. A candidate whose `rulesHash` is not the running world's is discarded and logged `CandidateDiscarded`.

### Phase 4 - Submit and nightly re-verification

**Targets:** none - infrastructure; the rejection cases, the replay verdicts and the runner budget are pinned by tests and by the Verification section

On top of [deployment-and-community.md](deployment-and-community.md) Phase 3 (sign-in, `POST /api/champions`, `checkUpload`, the pending queue, `verify-uploads.yml`). Where this phase changes that doc, the change is named here and made by T40.

#### Submit

- `js/app/ui/candidates.js` (`mountCandidates`) lists "Found in your world" in the Upload tab (`mountGeneUpload`): name, specialisation, tick, lineage depth, the hint (`clears` or not), and Submit per row. The prompt before the first submit states what is sent (the champion file and its provenance) and that the player's GitHub login is attached.
- The preference `autoSubmitCandidates` (default `false`, in `js/app/prefs.js`, `sanitizePrefs`) submits a candidate whose hint `clears` once signed in, at most one per hour per page, through the same endpoint, rate limits and Turnstile check as a manual submit (an invisible widget).
- The upload body is the champion file with the optional key `provenance`. `checkProvenance(provenance, { config })` in `js/library/provenance.js` runs inside `checkUpload` as check 3a: at most `MAX_PROVENANCE_BYTES` (4096) serialised; the keys of the Data table exactly; `seed` a non-negative integer; `rulesHash` equal to the `rulesHash` of the upload's season in `library/seasons.json`; `tick` an integer from 1 to `MAX_REPLAY_TICKS` (100000); `config` an object of keys `createConfig` knows, each valid, with `initialAgents` and `maxAgents` at most 500; `genomeIds` at most 64 non-negative integers; `poolIds` at most 50 content ids; `interventions` 0. Failure is `bad_field` naming `provenance` and the key. `canonicalChampion` ignores `provenance`, so a genome has one id however it is found.
- The `hint` is stored and shown; no check, rate decision, verdict or admission reads it. It is recomputed against the current pool's `poolBar` before each submit, so a hint made against an older pool is never shown.
- The "Found in your world" provenance badge on a verified row needs `replayable` true and a confirmed replay; a row verified by the exam and league after a `timeout` or `not_replayable` replay can enter the pool but carries no badge.

#### Re-verification

The nightly runner of `verify-uploads.yml` runs, for each pending row, in the `run` job (no secret), with the repo's own code at the sha it checked out (stored as `verified_sha`):

1. The checks of [deployment-and-community.md](deployment-and-community.md), Nightly verification, steps 2 to 5 (`season_closed`, `validateChampion`, the league).
2. The exam rows 1, 3 and 5 for the file (`js/evo/exam.js`: valid, drill, league) and the reflex score of its specialisation, giving `exam`.
3. `replayProvenance({ provenance, files, config, deadlineMs })` in `js/evo/provenance-replay.js`: when `provenance.replayable` is true, builds the world from `seed`, `config`, the policy and the pool files named by `poolIds` (read from `library/champions/<season>/` in the checkout), steps `tick` ticks, and requires that an alive agent has `genomeId` equal to the last of `genomeIds`, a lineage depth of at least `lineageDepth` and a weight row equal to the file's. The status is `confirmed`, `mismatch`, `timeout` (the deadline passed) or `not_replayable` (`replayable` false, or a missing pool file). `mismatch` rejects the row (`replay_mismatch`). `not_replayable` and `timeout` leave the row to the exam and league alone and are recorded.
4. `verdict({ elo, winRate, games, error, replay, exam })` in `js/library/verify-rules.js` adds to the existing verdict: `rejected` with `exam_failed` when rows 1 or 3 fail.

`POST /api/admin/verify` gains `replay` and `exam`. When the row is `verified`, the handler computes admission in the same D1 batch: `admitToPool({ row, pool })` in `js/library/pool.js` admits when the exam passes `poolBar` for its specialisation and `selectPool` over the pool plus the row keeps it; the row gets `in_pool` 1 and the displaced row `in_pool` 0 and `retired_at`. A verified row that is not admitted stays in the gene library and out of the pool.

Order within the night: `pickOrder` of [deployment-and-community.md](deployment-and-community.md) is unchanged; the replay runs after the league of the same row and counts in `nextFits`.

Runner budget. A replay is at most `MAX_REPLAY_TICKS` (100000) ticks of up to 500 agents: about 4.5 ms a tick on the trainer's core and 1.5 times that on a runner core, so at most about 11 minutes a row. T39 replaces the figure with a measured `npm run bench:parallel -- --counts 4` on the runner and sets `MAX_REPLAY_TICKS` from it.
