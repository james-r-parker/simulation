# Deployment and community

**Status:** Proposed - Phase 1 releases with Release Please, serves every release at `/v/<version>/` and the latest at `/`, deploys `main`, or the `season/next` line while one is open, to `/next/` and every same-repo PR to a preview; Phases 2 to 4 add a read-only gene library, verified community uploads and an `npx` contributor trainer.
**Validated:** 23eaea3 (2026-10-17)
**Priority:** 8 - the last stage: put v6 online, then open it to the community (user, 2026-10-16)
**Depends on:** [worker-and-renderer.md](worker-and-renderer.md), [evolution-rework.md](evolution-rework.md), [evolution-evals.md](evolution-evals.md), [v6-tidy-up-and-docs.md](v6-tidy-up-and-docs.md), [quality-gates-and-test-tiers.md](quality-gates-and-test-tiers.md)

The app is published on Cloudflare Pages by GitHub Actions, and then opened to the community:

- Phase 1 needs none of the other docs built, and is built at the end of v6: Release Please keeps a release PR open;
  merging it creates a GitHub Release, which builds the version, stores it in R2 under `/v/<version>/` and deploys it
  as the latest at `/`. A merge to `main` deploys `/next/` (while a `season/next` line is open, `/next/` serves that
  line instead); a PR gets a preview URL. The `main` ruleset is built: required checks `check` and `browser-smoke`.
- Phase 2 serves a library of champion files (R2 for the files, D1 for the index, Pages Functions for the API) and a
  "Gene library" drawer in the app. It is seeded with the project's own trained champions.
- Phase 3 accepts uploads from signed-in GitHub accounts at least 30 days old. Uploads are untrusted; a GitHub Actions
  run that starts when the nightly completes verifies them with the champion league, and only verified champions are ranked.
- Phase 4 publishes an npm package so a contributor runs `npx blob-evolution train --hours 8 --upload`.
- The other docs are needed by Phases 2 to 4: the renderer's app shell ([worker-and-renderer.md](worker-and-renderer.md) Phase 2), the trainer
  and `public/champions/v1/` ([evolution-rework.md](evolution-rework.md) Phase 3, behind its world gate), and the
  league ([evolution-evals.md](evolution-evals.md) Phase 4, built).

## Seasons

A champion is valid for one ruleset: its `rulesHash` (`rulesHash` in [config.js](../../js/sim/config.js)) and brain
layout (`brainLayout` in [brain-layout.js](../../js/sim/brain-layout.js)) must equal the running world's. The library
is organised in seasons, one ruleset each. The app and the drawer call a season "Ruleset N", because "season" also
names the in-world Spring to Winter cycle (`seasonLength`); `season` stays the field name in `seasons.json`, the API
and the champion rows.

- `library/seasons.json` is `[{ "season", "rulesHash", "layout": { "inputCount", "brainHidden", "outputCount" }, "opened", "major" }]`,
  oldest first. It is empty until the world gate in [evolution-rework.md](evolution-rework.md) Phase 3 passes. Season 6
  is the first entry (`major` 6), added in the PR that exports `public/champions/v1/`.
- A season is a major version: `major` equals `season`, a release `n.x.y` belongs to season `n`, and the npm package
  for season `n` is version `n.x.y`. Minor and patch releases stay within a season.
- A `conventions` test (`test/library/seasons.test.js`) fails when, on any branch but `season/next`, the newest entry's
  `rulesHash` differs from `rulesHash(createConfig())`; when a new entry's `major` is not the previous entry's `major`
  plus 1; when its `major` is neither the `package.json` major nor that major plus 1 (the release PR that bumps
  `package.json` makes them equal); or when its `opened` date is fewer than `MIN_SEASON_GAP_DAYS` (28, in
  `js/library/seasons.js`) after the previous entry's. The branch is read through `currentBranch()` in
  `scripts/lib/release-check.mjs` (`GITHUB_BASE_REF` or `GITHUB_REF_NAME` in CI, `git branch --show-current` locally).
- A change to `rulesHash` is a breaking change: its commit subject ends `!` (`feat(sim)!: ...`) or its body has a
  `BREAKING CHANGE:` footer, so Release Please bumps the major. `releaseCheck` ([Release check](#release-check)) fails a
  PR that changes `rulesHash` without one.
- The newest season is current. Older seasons stay listed and downloadable; their champions cannot be seeded into a
  newer ruleset (`canSeed` in `js/library/seasons.js`; the worker's `validateChampion` check repeats it).
- Uploads are accepted for the current season only. A pending upload of a closed season is rejected with reason
  `season_closed`.

### The next-season line

Rule changes batch on one long-lived branch, so a season opens at most every 4 weeks however many sweeps and rules
phases land in between.

| Item             | Rule                                                                                                                                                                                                                                                                                                     |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Branch           | `season/next`, created from `main` by the first PR that changes `rulesHash` once `library/seasons.json` has an entry, and deleted when the season opens. At most one exists. It has the same ruleset as `main` (required checks, strict, no force-push or deletion)                                      |
| Rules changes    | A PR that changes `rulesHash` (a sweep default, a rules phase) takes `season/next` as its base and carries a breaking commit. `releaseCheck` fails a PR whose base is `main` and which changes `rulesHash` without adding a `library/seasons.json` entry (reason `rules-change-on-main`)                 |
| Everything else  | Merges to `main`. The manager merges `main` into `season/next` by a PR (`chore/sync-season-next`, merge method) at least weekly while the line is open and before the season opens                                                                                                                       |
| Preview          | `/next/` serves `season/next` while it exists and the latest `main` otherwise ([Deploy workflow](#deploy-workflow)); `check.yml` runs on pushes to `season/next`                                                                                                                                         |
| Opening a season | One PR, `season/next` into `main`, merged with the merge method so its breaking commits reach `main`: a new `library/seasons.json` entry with its `major` and `opened`, retrained champions, `evals/league.json` repopulated (`--admit`). The release PR that follows bumps the package to `<major>.0.0` |
| Cadence          | `seasons.test.js` rejects an entry whose `opened` is under 28 days after the previous entry's                                                                                                                                                                                                            |

## Phases

### Phase 1 - releases, build and deploy pipeline

**Targets:** none - infrastructure; the deploy times in Performance budget are read from the Actions log

#### Release Please

`.github/workflows/release-please.yml` triggers on `push` to `main`. Its job `release-please` (environment `release`)
first runs `actions/create-github-app-token` (pinned to a full commit SHA, version in a comment) with `RELEASE_APP_ID` and
`RELEASE_APP_PRIVATE_KEY`, then `googleapis/release-please-action` (same pinning) with that token, `release-please-config.json`
and `.release-please-manifest.json`. The release PR is opened by the App, so it runs `check` and `browser-smoke` and can
satisfy the `main` ruleset; a PR opened with `GITHUB_TOKEN` starts no `pull_request` workflow and would never merge:

- Config: one package `.`, `release-type` `node`, `changelog-path` `CHANGELOG.md`, `include-v-in-tag` true,
  `bump-minor-pre-major` false. The manifest holds `{ ".": "5.0.0" }`, equal to `package.json` `version`; the
  config carries `"release-as": "6.0.0"` until the first release lands, so the first release is `6.0.0` (Season 6).
- From the conventional commits since the last release the action keeps one release PR open that edits `CHANGELOG.md`,
  `package.json` and the manifest. Merging it creates the tag `v<version>` and the GitHub Release.

| Commit                                         | Bump  |
| ---------------------------------------------- | ----- |
| `fix:`, `perf:`                                | patch |
| `feat:`                                        | minor |
| `!` after the type, `BREAKING CHANGE:` footer  | major |
| `docs:`, `test:`, `chore:`, `ci:`, `refactor:` | none  |

- `permissions` for the job: `contents: read`; the App token carries the write access, and the workflow default is `contents: read`.
- Outputs `release_created` and `tag_name` start the release jobs ([Release workflow](#release-workflow)) and, from
  Phase 4, `publish.yml`, in the same run.
- `CHANGELOG.md` and the `version` field of `package.json` are written only by the release PR.

#### Release check

`releaseCheck({ baseHash, headHash, messages, base, addsSeason })` in `scripts/lib/release-check.mjs` is pure. `isBreaking(message)` is true
for a subject `type(scope)!:` or a `BREAKING CHANGE:` footer. `releaseCheck` returns `{ ok: true }`, or `{ ok: false, reason: 'rules-change-not-breaking' }`
when `baseHash` differs from `headHash` and no message in `messages` is breaking, or `{ ok: false, reason: 'rules-change-on-main' }`
when `baseHash` differs from `headHash`, `base` is `main` and `addsSeason` (the PR adds a `library/seasons.json` entry) is false
([The next-season line](#the-next-season-line)). `scripts/release-check.mjs` is the
shell: it computes `rulesHash(createConfig())` at the merge base (in a temporary `git worktree`) and at `HEAD`, reads
the PR's commit messages, title and base, prints the verdict and exits 1 on failure. `check.yml` runs it on `pull_request`
events as the gate `release-check`; it logs `ReleaseCheckFailed` (reason, baseHash, headHash).

#### Release workflow

`.github/workflows/release.yml` is a reusable workflow (`on: workflow_call`, input `tag`; also `workflow_dispatch`
with the same input to repair a failed release) that `release-please.yml` calls when `release_created` is true.

> Note: The release jobs are called from `release-please.yml`, never triggered by the `release` or tag event. The
> release is created with the App token, which does start event workflows, so no workflow listens for the event and
> the release runs once. Verify this against the current GitHub documentation.

Jobs, in order:

- `build`: no secrets, `permissions: contents: read`. Checks out the tag with `persist-credentials: false`, installs Node with no `cache:`, runs `npm ci`, `scripts/check.sh --ci` and
  `npm run build:release -- <version>`, which writes `dist-release/` (Vite `--base /v/<version>/`), `dist/` (Vite
  `--base /`, the latest), `release-entry.json`, `upload-manifest.json` and `blob-evolution-<version>-dist.tar.gz`
  (the contents of `dist-release/`). It uploads these, `functions/`, `migrations/` and `wrangler.toml` as one artifact.
- `deploy`: `environment: production`, holds the secrets, `permissions: contents: write`, runs no repository `npm ci` or
  `npm run`, installs wrangler with `npm ci --ignore-scripts` in `.github/deploy/` (its own `package.json` and lockfile,
  `wrangler` pinned to the root `package.json` version), and runs, in order:
    1. `gh release upload v<version> blob-evolution-<version>-dist.tar.gz`.
    2. `node scripts/release-upload.mjs`: for each row of `upload-manifest.json`,
       `wrangler r2 object put matrix-releases/releases/<version>/<path> --remote` with the row's content type; then it reads
       `releases/index.json` from R2, applies `addRelease(index, entry)`, and writes it back (an identical entry is a
       no-op, so a repair run after a partial failure passes this step). It refuses any key outside
       `releases/<version>/` or any version that fails `isVersion`.
    3. In Phase 2 and later: `wrangler d1 migrations apply blob-library --remote` and the season sync.
    4. `.github/deploy/node_modules/.bin/wrangler pages deploy dist --project-name $PAGES_PROJECT --branch main` (production, the latest at `/`).
- Order matters: the versioned files and the index are in R2 before `/` changes, so the site never links a version that
  is not stored.
- `concurrency: release` with `cancel-in-progress: false`; the index is read, changed and written by one run at a time.
- Rollback: `workflow_dispatch` of `release.yml` with the previous release's tag rebuilds that tag and redeploys it to
  `/`; the index step is a no-op, so the site serves the older build and `/v/index.json` is unchanged. `DEPLOY.md`
  documents the command (`gh workflow run release.yml -f tag=v<version>`); `wrangler pages deployment rollback` is
  recorded in `DEPLOY.md` when T5 verifies that it exists.
- Logs: `ReleaseBuilt` (version, season, files, bytes), `ReleaseUploaded` (version, keys, wallMs), `ReleaseDeployed`
  (version, url, wallMs).

#### Versioned build and paths

| Path                 | Serves                                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `/`                  | The latest release (Pages production)                                                               |
| `/v/<version>/...`   | Release `<version>` forever, from R2 `releases/<version>/...`                                       |
| `/v/index.json`      | The release index                                                                                   |
| `/s/<season>/`       | `index.html` of the newest release of that season (its major); its assets load from `/v/<version>/` |
| `/s/<season>/<path>` | Redirect 302 to `/v/<version>/<path>` for the same release                                          |
| `/next/...`          | The `season/next` line while it exists, otherwise the latest `main`                                 |

- `vite.config.js` keeps `base: '/'`; the build overrides it with `--base`. It defines `__APP_VERSION__` (from the
  `APP_VERSION` environment variable, default `package.json` `version`) and `__SEASON__` (its major).
- Workers load with `new URL('./x.js', import.meta.url)`, and runtime fetches of files from `public/` prefix
  `import.meta.env.BASE_URL`. No path in the app starts with a bare `/` (except `/api/`).
- `releases/index.json` is `{ "releases": [{ "version", "season", "date", "rulesHash" }] }`, oldest first, written only by
  `release-upload.mjs`. `addRelease(index, entry)` (an entry equal to the stored one for its version is a no-op; a different entry for a stored
  version throws `release_conflict`) and `resolveSeason(index, season)` (the newest `version` whose
  `season` matches, or `null`) are in `scripts/lib/release-index.mjs`; `isVersion`, `releaseKey(version, path)` and
  `contentTypeOf(path)` are in `functions/_lib/releases.js`.
- `functions/v/[[path]].js` and `functions/s/[[path]].js` read the `RELEASES` R2 binding:
    - A version must match `^\d+\.\d+\.\d+$` and the key is `releases/<version>/<path>`; a path containing `..`, an
      empty segment or a backslash answers 404. Nothing outside `releases/` is listed or served.
    - Responses carry `contentTypeOf(path)` (`html`, `js`, `css`, `json`, `wasm`, `svg`, `png`, `woff2`, `txt`; others
      `application/octet-stream`) and `X-Content-Type-Options: nosniff`.
    - `/v/` responses use `Cache-Control: public, max-age=31536000, immutable`; `/v/index.json` and `/s/` use
      `public, max-age=60`. The handlers store and read them with the Cache API (`caches.default`).
    - An unknown version or season answers 404 `not_found` and logs `ReleaseNotFound` (kind, key).
- `functions/next/[[path]].js` forwards `/next/<path>` to `https://next.<PAGES_PROJECT>.pages.dev/<path>`: the deploy
  job for a push to `season/next`, or to `main` while no `season/next` exists, builds with `--base /next/` and runs `wrangler pages deploy dist --branch next`, which
  creates the preview deployment behind that alias (verify against Cloudflare's documentation). That deployment uses
  the `[env.preview]` bindings; `/api/` calls from a `/next/` page go to production.
- The app lists the releases in a "Versions" list (Phase 2, in the gene library drawer): version, season, date, a link
  to `/v/<version>/`, the current one marked with `__APP_VERSION__`.

#### Deploy workflow

`.github/workflows/deploy.yml` triggers on `workflow_run` of the `check` workflow ([check.yml](../../.github/workflows/check.yml))
completing; a deploy follows a passing gate only. It never deploys production; production follows releases
([Release workflow](#release-workflow)).

| `check` ran on                                      | Result                                                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `push` to `season/next`, conclusion `success`       | `/next/`: build with `--base /next/`, `wrangler pages deploy dist --project-name $PAGES_PROJECT --branch next` |
| `push` to `main`, `success`, no `season/next`       | The same `/next/` deploy                                                                                       |
| `push` to `main`, `success`, `season/next` exists   | `wrangler pages deploy dist --project-name $PAGES_PROJECT --branch main-latest`; no route points at it         |
| `pull_request` from this repo, conclusion `success` | Preview: the same command with `--branch pr-<number>`; the URL is commented on the PR                          |
| `pull_request` from a fork                          | Skipped, logged `DeploySkipped` with reason `fork`                                                             |
| any other conclusion                                | Skipped, logged `DeploySkipped` with reason `check-<conclusion>`                                               |

- Jobs, in order:
    - `plan`: no secrets. `scripts/deploy-plan.mjs` reads the `workflow_run` event JSON, the base branch's
      `wrangler.toml` and whether `season/next` exists (`git ls-remote --exit-code origin season/next`), and prints
      `action`, `branch`, `sha`, `pr` as `GITHUB_OUTPUT` lines. The pure part is
      `deployPlan({ event, repo, bindings, seasonNext })` in `scripts/lib/deploy-plan.mjs`; `readBindings(text)` in the same module reads
      the subset of TOML that `wrangler.toml` uses and throws on any other shape.
    - `build`: no secrets, `permissions: contents: read`. Checks out the run's `head_sha` with `persist-credentials: false`,
      installs Node with no `cache:` (a `workflow_run` build that wrote the npm cache would let PR code poison the
      default branch's cache), runs `npm ci` and `npm run build`, and uploads `dist/`, `functions/` and `migrations/` as one artifact.
    - `deploy`: `environment: preview`, holds the secrets and runs no repository `npm ci` or `npm run`. It checks out the

### Phase 3 - uploads and verification

**Targets:** none - infrastructure; the rejection cases and the runner budget are pinned by tests and by the Verification section

#### Sign-in

- Browser: `GET /api/auth/github` sets a `state` cookie (`HttpOnly; Secure; SameSite=Lax`, 10 minutes) and redirects to GitHub's authorize URL with no scopes;
  `GET /api/auth/callback` checks `state`, exchanges the code with `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`, calls
  `GET https://api.github.com/user`, upserts `users` (`github_id`, `login`, `github_created` from `created_at`), and sets the cookie `__Host-session`
  (HttpOnly, Secure, SameSite=Lax, Path=/, 7 days, HMAC-SHA-256 signed with `SESSION_SECRET`). The GitHub token is discarded.
  `POST /api/auth/logout` clears it. `GET /api/me` returns `{ githubId, login }` or 401.
- CLI: device flow against GitHub, then `POST /api/auth/device { githubToken }`. The Function first checks that the token
  was issued to this OAuth app with GitHub's verify endpoint, `POST /applications/{GITHUB_CLIENT_ID}/token` with
  Basic auth `GITHUB_CLIENT_ID:GITHUB_CLIENT_SECRET` (verify the path against GitHub's current API reference in T16a),
  and answers 401 `wrong_app` otherwise. It then reads `GET /user` with that token, upserts `users` (the same three fields), discards the token and returns `{ token, expires }`, an HMAC-signed bearer valid 30
  days. A blocked account gets 403 `blocked` from both.
- Modules: `js/library/session.js` (`signToken`, `verifyToken`, over WebCrypto, `now` passed in),
  `functions/_lib/auth.js` (`requireUser` (re-reads `users.blocked` on every request), `requireAdmin`, `requireVerifier`;
  each compares `Authorization: Bearer` in constant time, `requireAdmin` with `ADMIN_TOKEN` and `requireVerifier` with
  `VERIFY_TOKEN` or `ADMIN_TOKEN`).
- Stored personal data: GitHub numeric id, login and account creation time. No email, no token, no IP address.

#### Upload

`POST /api/champions` with the champion file as the body (`Content-Type: application/json`), cookie session or bearer
token. Browser requests add the header `X-Turnstile: <token>`, checked against `TURNSTILE_SECRET` through Cloudflare's
`siteverify`, whose response `hostname` must equal `SITE_DOMAIN` and `action` must equal `upload`; bearer requests skip Turnstile and are held to the same rate limits.
`checkUpload(bytes, { config, seasons })` in `js/library/upload-check.js` runs, in order, and the first failure wins:

| #   | Check                                                                                                                                                                                                  | Error code (field)               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| 1   | Body length at most `MAX_UPLOAD_BYTES` (65536), enforced on `Content-Length` and on the bytes actually read                                                                                            | `too_large`                      |
| 2   | UTF-8 JSON object                                                                                                                                                                                      | `bad_json`                       |
| 3   | Keys are exactly `version`, `name`, `rulesHash`, `layout`, `specialisation`, `weights` and optionally `cell`                                                                                           | `unknown_key` (the key)          |
| 4   | `validateChampion(file, config)` ([league.js](../../js/evo/league.js)): `version`, `layout.*`, `rulesHash`, `name`, `specialisation`, `weights`                                                        | `bad_field` (the field it names) |
| 5   | `name` at most 40 characters of `[A-Za-z0-9 _.-]`; `cell`, when present, an integer from 0 to `CELLS - 1` (`CELLS` in [archive.js](../../js/evo/archive.js), the format `train:export` writes)         | `bad_field` (`name`, `cell`)     |
| 6   | `isBlockedName(name)` (`js/library/name-filter.js`, new) is false: the name lower-cased, with `0 1 3 4 5 @ $` mapped to `o i e a s a s` and every ` _.-` removed, contains no entry of `BLOCKED_WORDS` | `bad_field` (`name`)             |
| 7   | Every decoded weight finite and at most `MAX_ABS_WEIGHT` (100) in magnitude                                                                                                                            | `bad_field` (`weights`)          |
| 8   | `rulesHash` equals the current season's; an older season's hash gives `season_closed`                                                                                                                  | `season_closed`                  |

Then, outside the pure check: not blocked (`blocked`); the GitHub account at least `MIN_ACCOUNT_AGE_DAYS` (30) old
(403 `account_too_new`, from `users.github_created`); the account within its limits (`rate_limited`: at most 5 uploads in a
rolling 24 h and 3 `pending` at once, `rateDecision({ uploads24h, pending })` in `js/library/rate-limit.js`; `accountAgeOk({ githubCreated, now })` in the same module); the whole
queue under 50 `pending` (`queue_full`, 503); `id` = SHA-256 of `canonicalChampion(file)`, and an existing `pending`, `verified` or
`removed` row answers 409 `duplicate`; then the R2 `put` of the canonical bytes and the D1 insert with `status` `pending`. The limits and the insert are one
conditional statement (`INSERT ... SELECT ... WHERE` the account's 24 h count, its pending count and the global pending
count are under their limits); zero changed rows is resolved to `rate_limited` or `queue_full` by a follow-up count. `assertGenomeFits`
([genome.js](../../js/evo/genome.js)) is not used: an upload is a champion file, and `validateChampion` is its check.

Pending rows older than 14 days are rejected `queue_expired` by `POST /api/admin/expire { olderThanDays }`, called at the
start of each verification run with `VERIFY_TOKEN`. `GET /api/me/uploads` lists the caller's rows with `status` and `reject_reason`.

#### Moderation

`scripts/library-admin.mjs` (`npm run library:admin -- <command>`), calling the admin endpoints with
`ADMIN_TOKEN` from the environment. `block` and `remove` accept `ADMIN_TOKEN` only; `queue`, `expire` and `verify` also

| Command                                               | Endpoint                  | Effect                                                                                |
| ----------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------- |
| `queue`                                               | `GET /api/admin/queue`    | Pending rows, oldest first, with `r2_key` and `uploader_id`                           |
| `block <githubId> --reason <text> [--remove-uploads]` | `POST /api/admin/block`   | `users.blocked = 1`; with the flag the account's rows become `removed`                |

#### Nightly verification

`.github/workflows/verify-uploads.yml` triggers on `workflow_run` of the `nightly` workflow (`completed`, only when
`head_branch` is `main`) and on `workflow_dispatch`, so it starts when the nightly is done however late the cron fired.
It checks out the default branch, runs `concurrency: verify-uploads` with `cancel-in-progress: false`, and has three
jobs joined by artifacts, so no job holds a secret and runs installed dependencies:

| Job     | Holds                                 | Runs                                                                                                                                                                                                              |
| ------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `fetch` | Environment `verify` (`VERIFY_TOKEN`) | `node scripts/library-verify-fetch.mjs`: no `npm ci`, `node:` built-ins and repo modules only. Expires old rows, orders the queue, writes `.sim/verify/` and uploads it as `queue`                                |
| `run`   | No secret                             | `npm ci`, then `node scripts/library-verify-run.mjs --deadline-minutes 280 --opponents 6 --workers 4`; its step has `timeout-minutes: 300`, the job 330; uploads `.sim/verify/` as `verdicts` with `if: always()` |
| `post`  | Environment `verify` (`VERIFY_TOKEN`) | `needs: [fetch, run]`, `if: always() && needs.fetch.result == 'success'`; no `npm ci`: `node scripts/library-verify-post.mjs` schema-validates `verdicts.jsonl` and sends each line                               |

The three entry scripts are thin shells over `scripts/lib/verify-schedule.mjs` (`pickOrder`, `nextFits`),
`scripts/lib/verify-queue.mjs` and `scripts/lib/verify-run.mjs`. A test asserts that the import closures of `fetch` and
`post` hold no bare specifier other than `node:*`. `test/workflows.test.js` covers `verify-uploads.yml` with the rules of
[Deploy workflow](#deploy-workflow): the job that runs `npm ci` sees no `secrets.*`, the jobs
that see `VERIFY_TOKEN` run no `npm ci`, and `post` is `if: always()`-gated on `fetch` only.

The verifier needs the current season's opponents in `evals/league.json`; the PR that opens a season repopulates it with
the new champions (`--admit`).

1. `fetch` calls `POST /api/admin/expire { olderThanDays: 14 }`, takes the whole queue (at most 50 rows) and orders it
   with `pickOrder(rows)`: round-robin by `uploader_id`, oldest first within each uploader, so no account takes the
   night twice before every other account with a pending row has had one.
2. For each row: download the file to `.sim/verify/<id>.json`; reject with `season_closed` when its `rulesHash` differs
   from `rulesHash(createConfig())` on `main`; run `validateChampion` again (`invalid` on failure).
3. `run` takes the next row only while `nextFits({ elapsedMs, lastMs, deadlineMs })` holds: always for the first row,
   after that while `elapsedMs + 1.25 * lastMs` is under `deadlineMs` (`--deadline-minutes` x 60000). Before a row's
   league it appends `{ id, started: true }` to `.sim/verify/verdicts.jsonl`; when the league ends it appends the
   verdict line `{ id, status, elo, winRate, games, reason }`, so a verdict is on disk the moment it is decided.
4. The league: `npm run league -- .sim/verify/<id>.json --opponents 6 --json`: 8 seeds against the first
   `--opponents` admitted champions of `evals/league.json`. The opponents are the project's own champions only, in file
   order. Uploaded champions are never admitted.
5. `verdict({ elo, winRate, games, error })` in `js/library/verify-rules.js`: `rejected` with `league_error` when a game
   threw, `below_floor` when `winRate` is under `MIN_WIN_RATE` (0.1), otherwise `verified`.
6. `post` calls `POST /api/admin/verify` for each verdict line. A row with a `started` line and no verdict (the job was
   killed mid-league) gets `POST /api/admin/attempt`; at 3 attempts the row is `rejected` with `verify_error`. A row
   the deadline never reached keeps `pending` and its `attempts`, and is first in line the next night for its uploader.

`scripts/league.mjs` gains `--opponents <n>` (default: all admitted) and `--json` (prints `{ elo, winRate, games }`).
Scores are written only by `post`; the upload body carries none. The 5 uploads a day limit is per account.

Runner budget. A league game is 100 agents for at most 50000 ticks (`MATCH_TICKS`, `MATCH_AGENTS` in
[league.js](../../js/evo/league.js)). The trainer's measured rate is about 7000 ticks/s over 32 workers
([evolution-rework.md](evolution-rework.md)), about 220 ticks/s per worker on that machine and at most 230 s per game
there. A hosted core is slower: about 4.5 ms a tick at 500 agents and 1.5 times that on a runner core gives about 340 s
for a 50000-tick game once a population grows toward `maxAgents`. T20 replaces both figures with a measured
`npm run bench:parallel -- --counts 4` on the runner.

| Quantity                                                       | Value                                                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Games per upload (8 seeds x 6 opponents)                       | 48                                                                       |
| Core time per upload                                           | at most 48 x 340 s = 16,320 s (replace with the T20 measurement)         |
| Wall time per upload on 4 workers (public-repo runner; verify) | at most 68 min                                                           |
| Job time budget                                                | 330 min job, 300 min `run` step, `--deadline-minutes` 280                |
| Uploads started per night                                      | While `nextFits` holds: 4 at the 68 min bound, more when games end early |
| Accepted per account per day / queue cap                       | 5 per account / 50 queue cap; a full queue clears in at most 13 nights   |

The repository is public; the minutes are free. `--deadline-minutes` is the one constant to change.

(`createApiClient`), `cli/season-check.mjs` (`checkSeason`) and `cli/constants.mjs` (`DEFAULT_API`, `GITHUB_CLIENT_ID`).

`npx blob-evolution train --hours <h> [--workers <n>] [--upload] [--run-seed <n>] [--out <dir>] [--api <url>] [--no-early-stop]`:

1. `checkSeason` fetches `GET /api/seasons`. When the current season's `rulesHash` differs from the package's, it exits 3
   with `npx blob-evolution@<major> ...` naming the matching package, before training anything. The server being
   unreachable exits 4 unless `--offline` (training only; `--upload` is refused with `--offline`).
2. With `--upload`, sign in first when no valid token is stored (device flow); a failure appears before the hours.
3. Train: the trainer ([evolution-rework.md](evolution-rework.md) Trainer) with `--checkpoint-every 10`. `--run-seed` (default
   random from `crypto.randomInt`, printed) seeds the stream `fork(createRng(runSeed), 'train-run')`, which T24 adds to the
   trainer (the stream is not defined in [evolution-rework.md](evolution-rework.md)); it orders the episodes, and run seed 0 leaves today's streams untouched. The same run seed reproduces the archive. The CLI stops after the generation that ends past `--hours`, or when
   `findPlateau` (learning curve) reports a plateau at least 10 generations old.
4. Export the five champions as `train:export` does into `<out>/champions/`, validate each with `validateChampion`.
5. With `--upload`, run `checkSeason` again, then `POST /api/champions` for each file, printing id and status; an upload
   rejected for `rate_limited` stops the loop and keeps the files.

`upload <file...>`, `login`, `logout` and `status` (own uploads) share the same client. The hidden flags `--generations <g>`, `--episodes <e>` and
`--episode-ticks <t>` (absent from `--help`, test use) replace the time budget and pass through to `scripts/train.mjs`. The token file is
`$XDG_CONFIG_HOME/blob-evolution/token.json` (`%APPDATA%\blob-evolution\token.json` on Windows), mode 0600; it holds the
API bearer only.

#### Publishing

`.github/workflows/publish.yml` is a reusable workflow (`on: workflow_call`, input `tag`; `workflow_dispatch` repeats a
failed publish) called by `release-please.yml` when a release is created: job `build` runs `npm ci`, `scripts/check.sh --ci`,
`npm run package:build` and checks `v` plus `dist-pkg/package.json` `version` equals the tag and that the tagged commit is an ancestor of `origin/main` (`git merge-base --is-ancestor`); job `publish` (environment
`npm-publish`, which waits for the user's approval) has `permissions: { contents: read, id-token: write }`, and runs
`npm publish dist-pkg --provenance --access public` with `NODE_AUTH_TOKEN` from the environment secret `NPM_TOKEN`.
After publishing, `npm audit signatures` in a clean install verifies the provenance attestation. Once the package exists, T29a switches to npm trusted
publishing (OIDC; verify that a trusted publisher accepts a reusable workflow called from `release-please.yml`) and removes `NPM_TOKEN`. The package's own dependencies: none. The repo's dev dependencies stay exact pins.

## Verification

1. `scripts/check.sh` is green on each phase's branch.
2. Phase 1: open a PR from a branch of this repo. After `check` passes, `deploy` posts one comment with a
   `pr-<n>.matrix.pages.dev` URL; the app loads there. Push another commit: the same comment updates. Open a PR from
   a fork: no deploy runs. Merge: `deploy` publishes `/next/` and `/next/` serves the new build; production is
   unchanged. A PR that changes `rulesHash` with a `feat:` commit fails `release-check`; with `feat!:` it passes against `season/next` and fails `rules-change-on-main` against `main`. While `season/next` exists, a merge to `main` publishes no `/next/` change. Re-dispatching `release.yml` with the previous tag serves the previous build at `/` and leaves `/v/index.json` unchanged.
   Release Please opens (or updates) one release PR listing the commits, and that PR shows `check` and `browser-smoke` results. Merge it: the tag `v<version>` and a GitHub
   Release with `blob-evolution-<version>-dist.tar.gz` exist, `release.yml` is green, `/v/<version>/` loads the app
   with every asset under `/v/<version>/`, `/` serves the same build, `/v/index.json` lists the release, and
   `/s/6/` loads the newest release of season 6. After a second release, `/v/<first version>/` still loads and `/`
   serves the newer one. `/v/9.9.9/` and `/v/6.0.0/../x` answer 404.
3. Phase 2: open the Gene library drawer on the production site. The Season 6 champions are listed; Download saves a
   file that `validateChampion` accepts; Seed world starts a new world with 12 clones of the champion, which behave like the champion's specialisation
   in the first minutes. A fake older-season row (inserted on the preview database) shows "Season N rules" and cannot
   be seeded. `node scripts/library-probe.mjs` meets the latency budget.
4. Phase 3: sign in with GitHub in the drawer, export a champion from a short local world and upload it with Turnstile:
   "My uploads" shows `pending`. Upload the same file again: 409 `duplicate`. Upload a file with one weight changed to

   listed. After the next nightly, the `verify-uploads` run starts by itself, is green, its log has `VerifyDecided`, and the row is `verified` with
   an Elo and a win rate in the list. `library:admin -- block <id>` makes the next upload answer `blocked`; `remove`
